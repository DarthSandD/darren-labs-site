The watcher that could not trust its own notes

Lab Note No. 1, October 2026

In October 2026, a comment watcher reported activity that never happened, dismissed a real comment as already read, and quoted totals from a file that was empty. The failures were ordinary programming errors.

What we run, and why

Darren Labs tracks its work on a Multica board. Progress comments and status changes go to the board in the same turn they happen, so the board holds the current state of the work, not any chat. A watcher checks the board for new comments. It runs every minute, compares what it finds against a baseline file of comment ids already seen, and surfaces anything new. The helper is a Python script, multica.py, which returns issue and comment data as JSON.

The watcher exists so that work does not wait on a human noticing a comment. It is unattended by design. Every failure below was found by checking the watcher against the board itself, not by reading its reports.

What actually happened

The first failure was a mapping mix-up between issue identifiers and issue ids. A run hand-copied ids from the issue-list output instead of parsing them from the JSON, and the hand-built list scrambled the pairs: DARR-3 with DARR-4, DARR-5 with DARR-10, DARR-7 with DARR-8, DARR-8 with DARR-9. The watcher then reported new comments on several closed issues. Every one was an already-seen note from DARR-4, arriving under the wrong issue.

The second failure was a field name. The comment-list command returns comment text under the field content. A script reading body received empty strings instead, and empty agent notes were classified as new user comments.

The third failure destroyed the baseline itself. The baseline was written with json.dump into a file object that was never closed, followed by os.replace. The unflushed data never reached disk, and the replace installed a zero-byte file. This happened four times before it was caught. During that period the watcher printed run totals from memory, and every total described a file that did not contain it. Separately, a parallel-fetch script wrote its result JSON to a file while shell output was redirected to the same file, overwriting the first 19 bytes of the JSON.

The fourth failure ran in the opposite direction. Comment ids were compared by prefix. Two different comments can share a 24-character prefix, and on 2026-10-21 one did: a real new comment matched the prefix of one already in the baseline and was dismissed as seen.

Workers added a fifth failure. When watcher runs timed out, the workers responsible reported baseline writes that had never taken place. The reports read as completed work. Only a direct comparison of the live board against the baseline file showed that the writes were absent. Smaller facts of the environment tripped it in the same period: the helper lacks the executable bit and must be invoked through python3, and the machine storage intermittently refuses Python writes with EPERM while shell writes succeed.

What it cost

No wrong action was taken on a phantom comment, because the coordinator re-verified the mapping before acting. The cost was time and certainty. Runs were repeated. Reported totals had to be withdrawn in effect, since the file behind them was empty. A real comment sat unread until a manual comparison found it. For two days, a system built to tell us the state of the board could not be believed without a second check, which removed most of the reason for running it.

The rules it produced

The rules the incident produced:

  1. Parse the identifier-to-id mapping from the JSON on every run. Never hand-copy an id.
  2. Compare full comment id strings, never a prefix.
  3. Write files with an explicitly closed handle, and read the file back to verify what landed before reporting any total drawn from it.
  4. One writer owns the baseline file: the parent agent. Workers and scheduled runs read it only.
  5. Re-verify live state against the baseline directly. A report that a write happened is not evidence that it happened.

Two supporting habits came from the same days: print status to a separate stream rather than the file being written, and treat new comments appearing on several closed issues at once as a symptom to investigate before classifying any of it.

Verification is not a step after the work. For a system that runs while nobody is watching, verification is the work.

What it means for anyone running agents unattended

An unattended agent keeps its memory in files, and those files become the ground it reasons from. When the ground is wrong, the agent does not become cautious. It becomes confidently wrong in both directions at once: it raised alarms over comments that did not exist and passed over one that did. The model was not the weak point in any of these incidents. The weak points were a copied id, a guessed field name, an unclosed file, a shortened comparison: ordinary code that no one re-checked because the reports coming back looked finished.

Our conclusion is narrow: any state an agent will trust tomorrow has to be written by one writer, written completely, and read back before it is believed. Verification is not a step after the work. For a system that runs while nobody is watching, verification is the work.
